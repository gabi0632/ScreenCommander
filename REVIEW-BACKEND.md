### 1. Express Route Order Bug: `/reload-all` and `/blackout-all` Never Reached

**File:** `packages/backend/src/routes/displays.routes.ts`, lines 82-133

The route `POST /api/displays/:id/content` is defined at line 82, followed by `GET /:id/screenshot` at line 92. The static routes `/reload-all` (line 116) and `/blackout-all` (line 126) are defined **after** the parametric `/:id` POST route at line 52.

For **POST** requests, Express evaluates routes in order. When a POST hits `/reload-all`, Express will match `/:id` first (with `id` = `"reload-all"`) at line 52 because `POST /` with `validate(createDisplaySchema)` is at line 52. Wait -- actually let me re-examine: the `POST /:id/content` at line 82 requires a sub-path `/content`, so `POST /reload-all` would not match that. However, the `POST /` at line 52 won't match `/reload-all` either because it's the root path.

**Re-assessment:** Express does match `POST /reload-all` to `POST /:id` patterns, but there is no bare `POST /:id` route -- only `POST /:id/content` and `POST /:id/identify`. Since `/reload-all` does not have a sub-path, it will correctly fall through to the `/reload-all` handler. **This is not actually a bug for POST.**

However, for **GET** requests: `GET /:id` (line 38) is defined before any other GET with a static prefix. If a client were to `GET /api/displays/reload-all`, it would be caught by `GET /:id` and try to look up a display with id `"reload-all"`. This is only a minor concern since reload-all is a POST endpoint.

**Verdict:** Downgraded -- not critical for the current route structure.

### 2. `POST /api/messages/dismiss-all` Caught by `POST /:id/dismiss` First

**File:** `packages/backend/src/routes/messages.routes.ts`, lines 52-70

`POST /:id/dismiss` is defined at line 52. `POST /dismiss-all` is defined at line 63. When Express receives `POST /api/messages/dismiss-all`, it will first try to match `/:id/dismiss`. The URL `/dismiss-all` does NOT have a sub-path after it, so `/:id/dismiss` requires the pattern `/{something}/dismiss`. Since `/dismiss-all` is a single segment, it will NOT match `/:id/dismiss`. It correctly falls through to `/dismiss-all`.

**Verdict:** Not a bug -- Express parametric routes with sub-paths don't match differently-structured URLs.

### 3. Content Upsert Uses Fabricated ID That Will Never Match Existing Records

**File:** `packages/backend/src/services/displays.service.ts`, lines 70-77

```typescript
const content = await prisma.content.upsert({
  where: { id: `${input.contentType}:${input.url}` },
  create: {
    type: input.contentType,
    url: input.url,
  },
  update: {},
});
```

The `where` clause uses `id: "${contentType}:${url}"` as a lookup key (e.g., `"WEB_URL:https://example.com"`). However, when the Content model creates records (both here and in `content.service.ts`), the `id` is auto-generated by `@default(cuid())` -- it will be something like `clxyz123...`, never `"WEB_URL:https://example.com"`.

This means the `upsert` will **never find an existing record** -- it will always create a new one. Every time content is assigned to a display, a duplicate Content row is created. Over time, this causes unbounded growth of the Content table with duplicate entries.

The `create` block here also does not specify `id`, so Prisma will auto-generate a cuid -- meaning the fabricated ID in `where` is completely useless.

**Expected behavior:** Should look up content by `type` + `url` (composite lookup), or use `findFirst` + conditional `create`.

### 4. Error Handler Will Never Be Called Due to 404 Handler Placement

**File:** `packages/backend/src/app.ts`, lines 36-41

```typescript
// 404 handler
app.use((_req, res) => {
  res.status(404).json({ error: 'Not found' });
});

// Global error handler
app.use(errorHandler);
```

The 404 catch-all handler at line 36 has the signature `(req, res)` -- two parameters. Express uses parameter count to distinguish error handlers (4 params) from regular handlers. Since the 404 handler **does not call `next()`** and always sends a response, the error handler below it will only be invoked if an **earlier route** calls `next(err)`. The 404 handler itself is fine for 404s.

However, the real issue is: if the 404 handler itself throws an error (unlikely but possible), the error handler below it would NOT catch it because Express identifies error handlers by their 4-parameter arity, and the 404 handler doesn't call `next(err)`. This is a minor concern.

**More importantly:** If any async route handler throws AFTER starting to send a response (e.g., double-response scenarios), the error handler cannot recover. But this is standard Express behavior, not specific to this code.

**Verdict:** The arrangement is actually correct for the common case. Routes call `next(err)` which skips the 404 handler and reaches the error handler. Downgraded to minor.

### 5. Path Traversal Vulnerability in Uploads Route

**File:** `packages/backend/src/routes/uploads.routes.ts`, lines 49-52

```typescript
uploadsRouter.get('/:filename', (req, res) => {
  const filePath = join(UPLOADS_DIR, req.params['filename']!);
  res.sendFile(filePath);
});
```

A malicious request to `GET /api/uploads/../../etc/passwd` (or the Windows equivalent `..\..\..\..\windows\system32\config\sam`) could escape the uploads directory. `path.join()` resolves `..` segments. `res.sendFile()` with an absolute path does NOT perform directory confinement.

This allows reading arbitrary files from the filesystem. While the project states it's localhost-only, this is still a serious vulnerability if the network config exposes port 3000 on LAN.

**Fix:** Validate that `req.params['filename']` contains no path separators or `..`, or use `res.sendFile(filename, { root: UPLOADS_DIR })`.

### 8. Scheduler Does Not Implement Recurrence Rules

**File:** `packages/backend/src/services/schedule.service.ts`, lines 62-145

The `checkSchedule()` function checks `startTime` and `endTime` but completely ignores the `recurrenceRule` field. The Prisma schema includes `recurrenceRule String?` and it's stored when creating entries, but the scheduler never evaluates it.

A schedule entry with `recurrenceRule: "0 9 * * MON-FRI"` (e.g., every weekday at 9 AM) would be treated as a one-time event based solely on its `startTime`/`endTime`.

**Expected behavior:** Parse `recurrenceRule` (cron expression) and calculate next occurrences to determine if the entry should be active now.

### 10. No Player Disconnect Handling -- Display Status Never Set to OFFLINE

**File:** `packages/backend/src/ws/gateway.ts`, lines 53-55


When a player disconnects (crashes, loses connection, etc.), the disconnect handler only logs a message. It does NOT:

```typescript
      displayId, status: 'OFFLINE',
    });
  }
});
```

### 15. `getActiveMessages()` Has Side Effects -- Called by Cleanup Interval and REST Endpoint

**File:** `packages/backend/src/services/messages.service.ts`, lines 25-74

The `getActiveMessages()` function both **reads** active messages AND **auto-dismisses** expired ones as a side effect. It's called:
1. By the REST endpoint `GET /api/messages/active` (line 19 of messages.routes.ts)
2. Every 10 seconds by the cleanup interval (line 243)
3. By `handlePlayerRegister` in the WebSocket events handler

When called concurrently (e.g., a REST request + cleanup interval fire at the same time), there's a race condition where both executions could try to dismiss the same expired messages simultaneously. While `updateMany` is idempotent, the `emit` calls would fire duplicate dismiss events to the dashboard and players.

### 16. `dismissMessage` Returns Stale Target Data

**File:** `packages/backend/src/services/messages.service.ts`, lines 150-174

```typescript

  where: { id },
```

The `include: { targets: true }` on the TextMessage update fetches the targets **before** the subsequent `updateMany` on MessageTarget. The `for (const target of message.targets)` loop at line 164 uses these stale targets to emit dismiss events, which is functionally correct (it iterates all targets), but the returned data to the REST client is stale.

### 17. `createMessage` Spreads Extra Fields Into Prisma Create

**File:** `packages/backend/src/services/messages.service.ts`, lines 83-99

```typescript
const { targetDisplayIds, ...messageData } = input;

const message = await prisma.textMessage.create({
  data: {
    ...messageData,
    scheduledAt: messageData.scheduledAt ? new Date(messageData.scheduledAt) : null,
    sentAt: messageData.scheduledAt ? null : new Date(),
    targets: { ... },
  },
});
```

The spread `...messageData` includes `scheduledAt` as a **string** (from the Zod schema: `z.string().datetime()`), but then immediately overrides it with `new Date(scheduledAt)`. The spread also includes `source: 'manual' | 'red-alert'` and `imageSize: number` which are valid Prisma fields. However, it also includes `imageUrl` which is optional -- if it's `undefined`, the spread won't set it, but if it's explicitly passed as `null` from the client, it could cause issues since the schema allows `String?`.

The real concern: `messageData.scheduledAt` is a string. The spread puts the string value into the Prisma create data, then the explicit `scheduledAt: ...` override correctly converts it to a Date. But if someone adds a field to the Zod schema that doesn't exist in the Prisma model, the spread would cause a runtime error.

### 19. Ticker `targetDisplayIds` Storage is Inconsistent

**File:** `packages/backend/src/services/ticker.service.ts`, lines 45-49

```typescript
if (input.targetDisplayIds !== undefined) {
  data['targetDisplayIds'] = Array.isArray(input.targetDisplayIds)
    ? JSON.stringify(input.targetDisplayIds)
    : input.targetDisplayIds;
}
```

When `targetDisplayIds` is an array, it's JSON-stringified before storage (e.g., `'["id1","id2"]'`). When it's the string `"all"`, it's stored as-is. But when reading it back in `getTargetDisplayIds` (line 148), the code checks:

```typescript
if (config.targetDisplayIds === 'all') { ... }
// else try JSON.parse
```

This works, but the Prisma model stores it as `String @default("all")`. The inconsistency between storing `"all"` as a plain string and arrays as JSON strings within the same column is fragile. If someone passes `targetDisplayIds: "all"` as an array element (i.e., `["all"]`), it would be JSON-stringified to `'["all"]'`, then on read it would be parsed as an array `["all"]`, not treated as the special "all" keyword.

### 20. Prisma Schema: `AppSettings.data` Is `String` but Spec Says `Json`

**File:** `packages/backend/prisma/schema.prisma`, line 104

```prisma
model AppSettings {
  id    String @id @default("singleton")
  data  String
}
```

The spec in `prompt.md` defines `data Json` but the actual schema uses `String`. While SQLite doesn't have a native JSON type (Prisma's `Json` type maps to text for SQLite), using `String` means Prisma won't provide any JSON-specific utilities and the application must handle serialization manually (which it does via `JSON.stringify`/`JSON.parse`). This is intentional for SQLite but diverges from the spec.
